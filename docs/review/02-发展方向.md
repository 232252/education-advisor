# Education Advisor 发展方向文档

> 基于 [01-调研报告.md](./01-调研报告.md) 的发现，给出产品与技术双线的演进路线。
> 核心判断：**先做减法和纠偏，再做加法**。当前最大的敌人不是缺功能，而是"承诺与实现的落差"（提示词承诺不存在的工具、文档承诺未实现的功能、多智能体名不副实）。

---

## 一、产品定位重申

这是一个**单机、隐私优先的班级教育管理 + AI 助教桌面软件**：
- 数据主权：Rust EAA 引擎本地事件溯源 + PII 加密，这是与 SaaS 竞品的根本差异点
- AI 价值：18 个角色化 agent + 本地 Ollama 支持，覆盖成绩分析/家校沟通/风险预警/周报生成
- 目标用户：一线班主任/科任教师（非 IT 人员），对"可信、稳定、看得懂"的敏感度远高于"功能多"

**发展主线**：把"隐私优先的班级 AI 助教"做实、做透，而不是铺开更多功能面。

## 二、必须先回答的三个战略问题

### Q1：18 个 agent 是资产还是负债？

**现状**：8 份提示词是模板残留、主 agent 人格为空、无委托机制、角色间差异仅剩 EAA 工具子集。

**方向判断：收缩为"少而真"**。
- 第一梯队（保留并做深）：main（总助教）、academic（成绩分析）、counselor（沟通建议）、weekly-reporter（周报）、class-monitor（班级动态）、risk-alert（风险预警）——这 6 个有真实使用场景且工具链支撑充分
- 第二梯队（合并/降级）：psychology+student-care 可合并为学生关怀；data-analyst+research 可并入 academic；executor/bug-hunter/validator/governor/supervisor 这类"系统维护类"角色对教师用户无感知价值，降级为内部 cron 任务而非用户可见 agent
- **诚实化**：要么实现真正的 main→specialist 委托路由（见 Q3），要么把宣传改为"18 种专家角色模板"。名不副实是信任杀手。

### Q2：飞书是核心场景还是可选集成？

**现状**：feishu-bot 链路工程质量高（队列/去重/背压/token 刷新），但硬编码只路由 main agent，且 main 的 SOUL 是空的。

**方向判断：飞书是第二入口，值得做实**。班主任在手机上收发飞书是真实高频场景。发展方向：
1. 先修复 main agent 人格与命令路由质量（当前空 SOUL + 模板 AGENTS 直接拉低飞书体验）
2. 支持飞书侧选择角色（@消息 + 角色前缀，如 `/academic 分析张三`）
3. 家长沟通草稿推送（counselor 生成 → 飞书发送）是最有价值的闭环

### Q3：要不要做真正的多智能体编排？

**现状**：SWARM_ARCHITECTURE.md 描述的蜂群架构无实现；pi-agent-core 也不含委托机制。

**方向判断：暂缓，用"轻量路由"过渡**。
- 全量编排（agent 间消息传递、共享黑板、结果聚合）复杂度高且调试困难，不符合"单机教师工具"定位
- **轻量路由方案**（建议 v0.2 实现）：main agent 获得一个 `delegate_to` 工具（参数：目标角色 + 任务描述），主进程直接 enqueue 对应 agent 的 runQueue，结果回传给 main 汇总。一次性约 150 行实现，即可让"调度其他 Agent"的承诺成真
- 全量蜂群从文档中移除或标注为"未实现的设想"

## 三、技术演进路线（五阶段）

### Phase 0：卫生与纠偏（1 个发布周期内，零功能变更）

| 目标 | 动作 | 理由 |
|---|---|---|
| 仓库减重 | 230MB 视频素材迁出 git（历史用 filter-repo 或接受历史保留只删 HEAD）；public/intro.mp4 移出安装包 | clone 慢、安装包大，且与产品无关 |
| 依赖清理 | 移除 chokidar/@tanstack/react-table/to-ico | 零引用，纯卫生 |
| 提示词重生 | 重写 main SOUL + 8 份模板 AGENTS + 去尾部自我复制 + 去硬编码人名 | **成本最低收益最大的单项改进**：直接影响每次 LLM 调用的 token 质量与成本 |
| 遗留物归档 | Dockerfile/install.sh/deploy//SWARM/single-agent/memory/ → docs/archive/ | 降低新人理解成本 |
| 文档对齐 | ROADMAP 多班级表述更新；docs/features/ 落空承诺修正 | 止损"文档撒谎" |

### Phase 1：正确性攻坚（紧随 Phase 0）

| 目标 | 动作 |
|---|---|
| 消灭类型撒谎 | cron:list/agent:get/skill:get catch 形状修复（白屏风险） |
| EAA 并发正确性 | 读写缓存竞态（写入序号校验）、abort SIGKILL 升级 |
| UX 错误闭环 | Dashboard 失败可见可重试、Settings 加载失败重试、Models 危险操作确认 |
| 补最致命测试 | pi-ai/streaming SSE 解析单测（所有 LLM 输出的底层） |

### Phase 2：架构统一（1-2 个周期）

| 目标 | 动作 |
|---|---|
| 渲染层数据层 | studentStore/classStore（带 TTL + 失效广播），消 4 域重复请求 |
| 组件归一 | 合并 TrendChart 双实现；Button/Skeleton 分批迁移（按域推进，每域一个 PR） |
| ipc 规则落地 | "域 >150 行或 ≥3 组 handler 才拆子目录"成文；params 必须复用 utils/sanitize；eaa-handlers 测试解耦 |
| 大文件拆分 | agent/execution.ts（system-prompt/continuation/event-collector）、eaa-bridge execution-policy、feishu-bot client-factory/guard |
| i18n 收口 | 438 处硬编码按域推进；或正式声明 zh-only 并删除 en 字典（二选一，忌拖延） |

### Phase 3：产品能力补全（2-3 个周期）

| 优先级 | 功能 | 依据 |
|---|---|---|
| P0 | Excel 学生批量导入（复用 agent 侧 files/excel-tools 的解析逻辑） | 用户最强需求；agent 已有 Excel 能力，只差 UI 入口，边际成本极低 |
| P0 | 完整自动更新（下载 + 重启安装） | 桌面软件分发的基础设施；CI 已产 latest.yml 只差消费端 |
| P1 | 轻量 agent 路由（delegate_to 工具） | 让多智能体承诺成真（见 Q3） |
| P1 | 自动备份调度（复用 cron 机制，settings 加开关） | 数据安全；backup-service 已齐备，缺调度接线 |
| P2 | 飞书角色选择 + 沟通草稿推送 | 见 Q2 |
| P2 | SQLite at-rest 加密评估（better-sqlite3 无 SQLCipher；务实方案是敏感字段应用层 AES，密钥走已有 keystore） | 补齐"隐私优先"叙事的最后一环 |

### Phase 4：质量与体验深化（长期）

- 打包产物冒烟进 CI（electron-builder + 启动探活）
- 提示词回归测试（18 角色的结构断言：无自我复制、无未注册工具引用、无硬编码人名——脚本化，进 doc:check 同类门禁）
- bootstrap 层（window/app-lifecycle）单测
- cron 错过调度补偿、飞书 401 自动重试等韧性项
- 打印能力扩展（家长报告已很好，可加班级学期报告）

## 四、明确不做的事（反向路线图）

| 不做 | 理由 |
|---|---|
| 插件市场/沙箱系统 | 单机场景无生态规模；skills 目录 + MCP 已够用 |
| 移动端/平板 | 数据同步复杂度与单机定位冲突；飞书入口已覆盖移动场景 |
| Tauri 重写 | 重写周期内产品零进展；Electron 痛点（体积）非用户核心痛点 |
| 全量蜂群编排 | 见 Q3 |
| 遥测/云端账户 | 与"隐私优先"根本冲突 |

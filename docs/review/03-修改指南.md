# 第一批 P0：正确性速修

## M1. 修复 cron:list 类型撒谎（白屏风险）

### 定位
- [src/main/ipc/cron-handlers.ts](../../src/main/ipc/cron-handlers.ts) L26-34
- 关联契约：[src/renderer/lib/ipc/cron.ts](../../src/renderer/lib/ipc/cron.ts) L8（`list(): Promise<CronTask[]>`）

### 现状证据（已人工核实）
```ts
ipcMain.handle(IPC.IPC_CRON_LIST, async () => {
  try {
    return cronService.listTasks()
  } catch (err: unknown) {
    const msg = err instanceof Error ? err.message : String(err)
    console.error('[IPC] cron:list failed:', msg)
    return { success: false, error: msg, tasks: [] }   // ← 类型撒谎
  }
})
```
渲染层 `CronAPI.list()` 声明返回 `CronTask[]`。`cronService.listTasks()` 抛错时（如 cron.user.json 损坏），渲染层拿到一个对象，`Scheduler` 页对返回值执行 `.map()/.filter()` 直接 TypeError → React 组件树崩溃。

### 多角度论证
1. **正确性**：契约先行原则——preload/渲染层的类型声明就是 API 契约，catch 分支返回不同形状是"类型撒谎"。F3 修复已确立先例（cron:get-logs catch 返回 `[]`），本处是漏网之鱼。
2. **替代方案对比**：
   - 方案 A（选定）：catch 返回 `[]` + console.error。与 F3 模式一致，零渲染层改动。
   - 方案 B：渲染层做防御性 `Array.isArray(res) ? res : []`。治标不治本，且 17 个 IPC 域都要加一遍。
   - 方案 C：改契约为 `{success, tasks}` 联合类型。破坏所有现有调用方，收益不成比例。
3. **用户体验**：cron.user.json 损坏属罕见场景，返回空列表 + 控制台日志 + （可选）toast 提示，比白屏好一个量级。
4. **风险**：几乎为零——返回 `[]` 后 Scheduler 页显示空任务列表（本来 service 抛错时用户也得不到任何数据）。

### 具体改法
```ts
ipcMain.handle(IPC.IPC_CRON_LIST, async () => {
  try {
    return cronService.listTasks()
  } catch (err: unknown) {
    const msg = err instanceof Error ? err.message : String(err)
    console.error('[IPC] cron:list failed:', msg)
    return []   // 契约是 CronTask[]；与 F3（cron:get-logs 返回 []）模式对齐
  }
})
```

### 验证方法
1. 单测：在 `tests/main/cron-service.test.ts` 或新建用例中 mock `cronService.listTasks` 抛错，断言 handler 返回 `[]`。
2. 手工：临时在 `cronService.listTasks` 首行插入 `throw new Error('x')`，启动应用进 Scheduler 页 → 应显示空列表而非白屏；验证后移除。

### 回滚
单行改动，git revert 即可。

## M3. Models 页危险操作加确认弹窗

### 定位
- [src/renderer/pages/Models/hooks/useModelsData.ts](../../src/renderer/pages/Models/hooks/useModelsData.ts) L112（删除 API Key）、L230（删除自定义模型）

### 现状证据
删除 API Key / 删除自定义模型直接执行，无 ConfirmDialog。对照组：Settings 页 reset/clearLogs 都有双确认（SettingsPage.tsx:138-139），Students 删除学生有 ConfirmDialog（StudentsPage.tsx:238-244）。同一应用内危险操作确认标准不一致。

### 多角度论证
1. **数据安全**：API Key 删除后用户需重新粘贴（keystore 不可恢复）；自定义模型删除丢配置。误触成本高。
2. **一致性**：项目已有 `ConfirmDialog` 组件与 `useConfirmDialog` hook（components/ConfirmDialog.tsx 95 行 + hooks/useConfirmDialog.ts 28 行），迁移成本是"接线"而非"造轮子"。
3. **替代方案**：仅 toast 提示"已删除"——已实施但不够，toast 是事后通知非事前拦截。

### 具体改法（模式参考 SettingsPage.tsx:138-139）
```tsx
// useModelsData.ts 内新增（或由页面层持有 confirm 状态）：
const [pendingDelete, setPendingDelete] = useState<{type:'apiKey'|'model', id:string} | null>(null)

// 原直接执行处改为 setPendingDelete({...})
// 页面 JSX 挂载：
<ConfirmDialog
  open={!!pendingDelete}
  title={t('page.models.confirmDeleteTitle')}
  description={...}
  danger
  onConfirm={() => { doDelete(pendingDelete); setPendingDelete(null) }}
  onCancel={() => setPendingDelete(null)}
/>
```

### 验证
手工：Models 页点删除 → 出现确认框 → 取消不执行 / 确认执行。已有 `ConfirmDialog.test.tsx` 组件测试可参照补一条。

## M4. Settings 页加载失败提供重试

### 定位
- [src/renderer/pages/Settings/SettingsPage.tsx](../../src/renderer/pages/Settings/SettingsPage.tsx) L152-157（catch 仅 toast）、L199-205（`if (loading || !settings)` 永久渲染"加载中"文本）

### 现状证据
settings 加载失败 → toast 一闪而过 → `settings` 永远是 null → 页面永久停留在"加载中"，无任何出口。用户唯一恢复手段是重启应用。

### 多角度论证
1. **状态机完整性**：加载态三态（loading/error/ready）中 error 态缺失。这是 UI 状态机的教科书缺口。
2. **方案对比**：仅加"重试"按钮（选定，最小改动）vs 全局 ErrorBoundary 接管（过重，且 ErrorBoundary 是崩溃兜底不该承担业务错误态）。
3. **一致性**：Academics 页已有 `gradesError + onRetry` 模式（AcademicsPage.tsx:63、OverviewTab.tsx:65），直接复制该模式。

### 具体改法
```tsx
// 1. 增加 error 态：const [loadError, setLoadError] = useState<string | null>(null)
// 2. loadSettings 的 catch 里 setLoadError(msg)（保留 toast）
// 3. 渲染分支：
if (loading) return <PageSkeleton ... />          // 顺手用 Skeleton 统一加载范式
if (!settings) return (
  <EmptyState
    title={t('page.settings.loadFailed')}
    description={loadError ?? undefined}
    action={<Button onClick={loadSettings}>{t('common.retry')}</Button>}
  />
)
```

### 验证
手工：临时把 `settings:get` handler 改为抛错 → Settings 页显示错误态 + 重试按钮 → 恢复 handler → 点重试回到正常。

## M5. Dashboard 部分失败可见化

### 定位
- [src/renderer/pages/Dashboard/DashboardPage.tsx](../../src/renderer/pages/Dashboard/DashboardPage.tsx) L81-87（已人工核实：`console.warn`，注释自述"仅 console.warn，不弹 toast"）

### 现状证据
8 路数据（useMultiLoader 的 errors）失败只进控制台。用户看到的是空图/零值，无从分辨"没数据"与"加载失败"。

### 多角度论证
1. **信息架构**：Dashboard 是首页，首因效应最强。8 卡中任何一张静默失败都在侵蚀信任。
2. **方案对比**：
   - 方案 A（选定）：卡片级降级——`useDashboardData` 已返回 per-source errors，把 error 传给对应卡片组件，卡片内部把 EmptyState 的 title 换成"加载失败"+ 重试按钮。粒度最细，局部失败不影响其他卡。
   - 方案 B：顶部聚合告警条（"3 项数据加载失败，点击重试"）。实现更快但信息粗。
   - 方案 C：维持现状。不可接受——与 useMultiLoader 设计初衷（"errors 不弹 toast、由页面呈现"）矛盾，页面根本没呈现。
3. **工作量**：Dashboard 各卡组件已统一接收 props，加一个可选 `error?: string | null` prop 改动面可控。

### 具体改法
1. `useDashboardData.ts`：把 `errors` 对象从 hook 返回值暴露（如已暴露则确认页面拿到）。
2. DashboardPage 逐卡传 `error={errors.ranking}` 等。
3. 各卡组件（RankingCard/ScoreDistChartCard 等）：`if (error) return <EmptyState title={t('common.loadFailed')} action={<Button size="sm" onClick={onRetry}>…}</Button>}`。
4. `onRetry` 用 useMultiLoader 的 `reload()`。

### 验证
手工：断网启动应用 → 各卡显示"加载失败+重试"而非空图；恢复网络点重试恢复。

## M7. webContents.send 增加 isDestroyed 守卫

### 定位
- [src/main/services/cron/task-executor.ts](../../src/main/services/cron/task-executor.ts) L65（熔断分支，在 try 块外）
- [src/main/services/cron-service.ts](../../src/main/services/cron-service.ts) L294（broadcastStatus）

### 现状证据
窗口销毁后 `webContents.send` 抛 "Object has been been destroyed"。task-executor 的熔断分支在 try 之外，异常会逃逸到 node-cron 回调。对照组：agent 链路的 `sendAgentStatus` 已有守卫——同项目两种标准。

### 论证
- **稳定性**：用户关窗后 cron 仍在跑（托盘模式/退出延迟），此处是真实可达路径而非理论风险。
- **修复成本**：每处一行 `if (!win || win.isDestroyed()) return`。

### 具体改法
两处 send 前加：
```ts
if (!win || win.isDestroyed()) return
win.webContents.send(...)
```
**建议顺手全仓统一**：grep `webContents.send` 的所有调用点（约 10+ 处），抽一个 `safeSend(win, channel, payload)` 工具（可放 src/main/utils/），逐点替换——一次消除整类问题。

### 验证
`npm run typecheck && npm test`；手工：启动应用 → 触发一个 cron 任务 → 任务执行前关闭主窗口（保留进程）→ 控制台无 "Object has been destroyed"。

## M9. 重写 agents/main/SOUL.md（当前 0 字节，已核实）

### 多角度论证
1. **产品角度**：用户在 Chat 页/飞书对话的第一体验由 main 定义。
2. **技术角度**：SOUL.md 每次运行注入 system prompt 头部（最高权重位置），空文件浪费最高价值 token 位。
3. **写作原则**（避免重蹈覆辙）：
   - 只描述运行时**真实存在**的能力（工具清单以 agent/tools.ts + eaa/tools/registry.ts 为准）
   - 不引用 exec/memory/HEARTBEAT 等未实现机制
   - 不硬编码用户数据（"52 个学生""邵老师"）
   - 中文为主（目标用户中文教师），控制在 60-120 行

### 参考骨架
```markdown
# 角色
你是"班级智脑"——一位经验丰富的班主任 AI 助教，运行在教师的本地电脑上，数据不出本机。

# 核心职责
1. 理解教师意图，直接调用工具完成查分、统计、事件记录
2. 涉及深度分析（单科诊断、对比、风险）时给出结论 + 依据 + 建议动作三段式回答
3. 主动提醒可用的下一步（如"可以让我生成周报"）

# 可用能力（如实）
- 学生查询：score / history / ranking / search
- 事件记录：add-event / revert（写操作需向教师复述确认）
- 数据导出：export CSV/JSONL
- 本地文件读写（仅限用户指定路径）

# 边界
- 不编造学生数据；查不到就说查不到
- 写操作前必须复述内容请教师确认
- 涉及学生隐私的信息在输出中默认脱敏（可用 privacy 工具）
```
（具体能力清单以实际 registry 为准——执行时先读 `src/main/services/eaa/tools/registry.ts` 核对。）

### 具体改法（步骤）

## M12. eaa-bridge 抽取 execution-policy（消 4 个重复重试块）

### 定位
- [src/main/services/eaa-bridge.ts](../../src/main/services/eaa-bridge.ts) L282-290（读分支 os error5 重试）、L294-301（读分支空 stdout 重试）、L331-339（写分支 os error5）、L341-348（写分支空 stdout）

### 现状证据
读/写两分支的"os error 5 重试 2 次"与"空 stdout 重试 2 次"是逐字相同的模式，共 4 份。

### 多角度论证
1. **DRY**：4 份重复意味着下次调整重试策略（如 Windows Defender 高发期加到 3 次）要改 4 处，漏 1 处即行为分裂。
2. **可测性**：抽成纯函数 `runWithTransientRetries(run, kind)` 后，可以直接单测重试语义（现在只能经真实 spawn 集成测试覆盖）。
3. **方案对比**：装饰器模式（过度）vs 类继承（不适合函数式风格）vs 简单高阶函数（选定，项目已有 withTimeout 同款先例）。

### 具体改法
```ts
// 新文件 src/main/services/eaa/execution-policy.ts
export async function runWithTransientRetries<T>(
  run: () => Promise<T>,
  classify: (t: T) => 'ok' | 'osError5' | 'emptyStdout' | 'fatal',
  opts: { maxRetries?: number } = {},
): Promise<T> {
  const max = opts.maxRetries ?? 2
  let last: T
  for (let attempt = 0; ; attempt++) {
    last = await run()
    const kind = classify(last)
    if (kind === 'ok' || kind === 'fatal' || attempt >= max) return last
    await sleep(kind === 'osError5' ? 250 * (attempt + 1) : 100 * (attempt + 1)) // 与现有退避对齐
  }
}
```
eaa-bridge 的读/写分支各自只保留 classify 闭包（判断 os error 5 / 空 stdout），重试循环删除。execute 主体预计减 80-100 行。

### 验证
现有 eaa-bridge 测试（真实 spawn + sigkill/writequeue 系列）必须全绿——这是"纯重构行为零变化"的硬标准。补 3 条 execution-policy 单测（ok 不重试 / osError5 重试后成功 / 超次数放行）。

## M13. 修复 EAA 读写缓存竞态（本批最重要的正确性修复）

### 定位
- [src/main/services/eaa-bridge.ts](../../src/main/services/eaa-bridge.ts) L262-306（读路径，L303-305 set 缓存）与写路径 L310+（clear）

### 现状证据（复现场景）
1. 读命令 R 启动：查缓存 miss → await 写队列（空，直接过）→ spawn EAA → 得到旧快照
2. 写命令 W 插队（agent 工具写 EAA 与 UI 读并发）：W 执行成功 → `readCache.clear()`
3. R 完成，L303-305 把**步骤 1 的旧快照 set 回缓存** → 之后 10s 内所有读命中过期数据

代码注释只承认"读到旧快照"（可接受），未意识到旧快照会**驻留缓存**（不可接受）。

### 多角度论证
1. **正确性**：这是"读-写-读"数据一致性经典问题。教育场景里 = 教师录入事件后看板 10 秒不更新，触发"我是不是没保存成功"的信任危机。
2. **方案对比**：
   - 方案 A（选定）：**写序号校验**。execute() 持有 `writeSeq` 计数器，每次写命令成功后 `writeSeq++`。读路径在 spawn 前记录 `seqBefore = writeSeq`，set 缓存前检查 `writeSeq === seqBefore`，不等则丢弃 set。约 8 行改动，精准封住窗口。
   - 方案 B：写命令完成后 invalidate 时记 key 时间戳，读 set 时比对——本质同 A 但状态散在两处。
   - 方案 C：读命令完成后无条件跳过缓存（性能倒退，不取）。
   - 方案 D：写命令期间暂停读缓存写入（读写锁）——并发度损失大，复杂度高。
3. **性能**：方案 A 零常态开销（一次整数比较）。

### 具体改法
```ts
// eaa-bridge.ts 类字段：
private writeSeq = 0
// 写命令成功路径（现有 clear() 附近）：this.writeSeq++
// 读路径：
const seqBefore = this.writeSeq
const result = await this.processExecutor.execute(...)   // 现有 spawn 调用
// ... 现有重试逻辑（重构后经 execution-policy）...
if (this.writeSeq === seqBefore) {
  this.readCache.set(cacheKey, result)   // 竞态窗口内放弃 set，下次读自然拿新数据
}
```

### 验证
1. 单测（关键）：模拟 executor 返回 pending promise，在读 in-flight 时插入一次写调用，断言缓存未写入旧快照。eaa-bridge 现有测试基建（可注入 fake executor）支持此写法。
2. 手工：Students 页添加事件 → 立即切 Dashboard → 数据应含新事件（当前版本有概率 10s 内不含）。

### 风险
低。竞态时放弃缓存 set 只会导致一次多余 spawn（拿新数据），无正确性风险。

### 设计

4. **风险**：串行等待 specialist 完成才回 main，长任务下 main 响应变慢——对单机教师场景可接受（本来就是异步等待，UI 有 live-output）。

# Education Advisor 发展方向文档（第二轮 · R2）

> 基于 [01-调研报告-2026-08-27](./01-调研报告-2026-08-27.md) 的发现，给出产品与技术双线的演进判断。
> 核心判断延续 R1 并更新：**R1 解决了「承诺与实现的落差」的内部欠账（M1-M35 + f6e8d36），R2 的主要矛盾转移到「外向能力」**——AI 懂业务但触达不了家长、周报产得出但看不见、隐私承诺了但旁路存在、官网建成了但指错版本。
> 日期：2026-08-27

---

## 一、产品定位重申（不变）

单机、隐私优先的班级教育管理 + AI 助教桌面软件。目标用户是一线班主任（非 IT 人员），对「可信、稳定、看得懂」的敏感度远高于「功能多」。R1 定下的「先做减法和纠偏，再做加法」在本轮依然成立——但减法已基本做完（18 agent 全部真实、提示词成体系、无 mock），**本轮的重心是「把承诺的最后一公里修完」**。

## 二、本轮必须回答的四个战略问题

### Q1：AI 对业务的理解，7 分之后怎么涨到 9 分？

R1 之后 AI 的「业务世界观」已经完整（project-context 注入 + 15 个实时数据工具 + 统一阈值）。剩余 3 分的缺口按优先级：

1. **班级元数据注入（最高性价比）**——「懂操行分业务」≠「懂你这个班」。教师问「我们班最近怎么样」，AI 需要立刻知道：年级、班级名、学生数、科目构成、本学期时间范围。这些数据**已经在 SQLite classes 表里**，只差注入。这是所有改进里「一行数据换一分体验」最划算的。
2. **意图路由**——现状把「选对 agent」的责任推给教师。班主任不该需要理解 18 个 agent 的分工。方向：Chat 入口默认 main，由 main 的 delegate_to 承担路由（机制已存在），再补一个轻量的意图提示层（在 main 的 AGENTS.md 中给出「哪类问题转给谁」的路由表——**不需要写代码，改提示词即可**）。
3. **记忆从「能用」到「在用」**——记忆功能 8-27 才上线，零沉淀。需要两个动作：a) 首次对话引导（onboarding 或 main 的 SOUL 里加「记住教师偏好」的主动询问策略）；b) 修掉记忆不经脱敏的缺陷，否则记忆越积越多，脱敏漏洞越大。
4. **技能库从 1 个文件到体系**——当前唯一技能 STUDENT_MANAGEMENT.md 与公共规则重复。方向不是多写技能文档，而是把 docs/SOP.md、AGENT_AUTHORING.md 里已经存在的操作知识改编成技能，让 AI 可调用。

**明确不做的**：RAG/embedding 检索。当前数据规模（一个班 ≤ 数百实体）下，全量注入 + 实时工具查询比向量检索更准、更简单、零依赖。这条边界 R1 已划，本轮维持。

### Q2：「给家长发提醒」——做，还是明确不做？

这是本轮最重要的产品决策。事实：班主任场景下「家校沟通」是高频刚需，但：
- 现状链路断在最后一公里（无出站工具，F-03）；
- 家长的飞书 openId 名册不存在（需要教师逐个维护，或接企业微信/钉钉/短信——每条都是大工程）；
- main 的 SOUL 已把「家长沟通」列为敏感动作。

**判断：分两步走。**
- **短期（R2 内）：诚实降级**。明确产品口径为「AI 起草、教师发送」——AI 生成话术（这个已经做得很好，counselor/home_school 角色就是干这个的），教师复制后通过自己的渠道发送。同时修掉「AI 假装能发」的误导（见 03 指南 R2-06）。
- **中期（R2 之后）：受控出站**。若教师群体确有强需求，做一个 `feishu_send_to_parents` 工具：绑定家长 openId 名册（本地维护）、每次发送前必须经教师在 UI 上确认（复用现有 ConfirmDialog 模式）、走已有的隐私脱敏管线。**不做静默发送**——这是隐私优先产品的底线。

### Q3：隐私优先，是口号还是承诺？

现状：隐私引擎（Rust 加密映射 + TS 边界脱敏）工程质量高，但存在两个「承诺裂缝」：
1. file/excel/MCP 工具是脱敏旁路（F-04）——开启脱敏的用户以为安全，实际 agent 读个 Excel 真名就出去了。**必须修**，否则「隐私优先」这个核心卖点经不起一次认真审视。
2. 引擎默认关闭（enabled=false）——产品选择可以理解（首启体验），但 onboarding 向导（已存在，385 行 5 步骤）应当加一步显式的隐私选择，让「关闭」成为用户的知情决定而非默认无知。

**判断：隐私是本项目与 SaaS 竞品的根本差异点（README 自己也这么宣传），值得投入使其无懈可击。R2 内封堵旁路，R3 考虑默认开启引导。**

### Q4：官网与发布工程——事故怎么防？

F-01/F-02（下载页指错版本、Release Notes 拉错仓库）是**上线级事故**：用户点下载按钮得到 404 或装上一个不同产品线的旧版本。根因不是写错了链接，而是**官网与仓库没有单一事实来源**——版本号、下载地址、release 仓库各自手抄。

**判断：三件事。**
1. 立即修错（动态解析 GitHub API latest release，删除硬编码）；
2. 官网独立化（site-build 拆独立仓库或至少独立 CI，与桌面应用解耦——它已经有自己的 wrangler.toml，本来就是两个交付物）；
3. 建立版本单一来源：package.json version → 注入 AboutSection（顺带修 F-23 版本号写死）→ 官网动态获取。**任何手抄版本号的地方都是未来的事故**。

## 三、技术债的取舍（哪些修、哪些留着）

**必须修（影响正确性/可信度）**：
- 数据目录 4 套解析分叉（F-05）——这是唯一会**丢数据**的架构债（备份打包旧副本、dev/prod 视图分裂）。修法是统一 path-resolver，不是重写数据层；
- 2 处工具声明断链（F-06）——提示词教模型调用不存在的工具，直接损害「AI 可信」；
- 死配置清理（F-16）——「可配但不生效」对非 IT 用户是欺骗性伤害。

**值得修（结构性改善，渐进进行）**：
- path-resolver 统一 → agent-service 拆分 → feishu 领域合并 → ipc 子目录化。按此顺序，每步独立可验证；
- 重复小函数收敛、45 处 select 抽公共组件——一次卫生 PR。

**明确留着（有意识地接受）**：
- 三层缓存叠加（bridge 10s TTL + ipc 闭包 cache + renderer store）：复杂但有 writeSeq 序号 + writeListener 三重粘合，正确性成立。**新增写路径时必须接入 writeListener**——这条写进开发文档即可，不值得重构；
- vendor 944 文件：有 verify-vendor.mjs 锁定，file: 依赖是这个 pi-ai 生态的现实选择；
- Dashboard 前端聚合：班级规模（≤100 人）下 5000 条上限可撑很久，等真实数据量逼近再做后端聚合。

## 四、R2 路线图（与 03-修改指南的批次对应）

| 阶段 | 主题 | 内容 | 预期效果 |
|---|---|---|---|
| R2-A（0.5-1 天） | 止血 | R2-01～04：官网链接、工具断链、死配置、git 推送 | 消除全部事故级与「AI 说谎」问题 |
| R2-B（2-4 天） | AI 懂「你」 | R2-05～11：班级上下文、家长触达降级口径、脱敏旁路封堵、记忆引导、意图路由、模型分流、技能扩充 | AI 理解度 7→8.5 分；隐私无懈可击 |
| R2-C（2-3 天） | 功能收口 | R2-12～16：周报中心页、i18n、Ollama 兜底、状态条、memo、版本号 | UI 完善度 8→9 分 |
| R2-D（3-5 天，渐进） | 架构收口 | R2-17～23：path-resolver、agent-service 拆分、feishu 合并、ipc 归一、重复收敛 | 数据不再有丢失风险；新人可导航 |
| R2-E（0.5 天） | 仓库卫生 | R2-24～27：视频瘦身、tracked 残留、文档漂移、官网独立化决策 | 仓库 -12MB+，文档可信 |
| R2-F（1-2 天） | 测试补强 | R2-28～30：feishu 出站直测、chat 组件测试、周报 e2e | 新链路有回归保护 |

**节奏建议**：A 批次立即做（当天可完成）；B 批次是本轮灵魂（用户价值最高）；C/D 可交错；E/F 收尾。R2 完成后建议发 v0.1.0-rc.2 并推送全部提交。

## 五、R3 展望（本轮不做，先立靶）

1. 家长名册 + 受控出站发送（Q2 中期方案）；
2. 隐私引擎默认开启 + onboarding 隐私步骤；
3. 纯规则即时预警（事件写入 → 分数跌破阈值 → 本地通知，不等 LLM 定时任务）；
4. 后端聚合的 Dashboard（若真实数据量增长）；
5. 官网独立仓库后的双语官网（当前纯中文，产品 README 是英文——受众错位）。

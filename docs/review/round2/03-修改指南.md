# 第一批 R2-A：止血（预计 0.5 天）

## R2-01 官网下载页修复（事故级，最高优先）

### 定位
- `site-build/download.html:135-174` —— 5 个下载按钮硬编码 `releases/download/v3.2.0/Education-Advisor-3.2.0-Setup.exe` 等链接
- `site-build/js/download.js:5,34` —— `REPO_NAME = 'education-advisor-tauri'`，从**错误仓库**拉 Release Notes

### 现状证据
- 本仓库 package.json version 为 `0.1.0-rc.1`，从未发布过 v3.2.0 —— 线上按钮全部 404；
- download.js 的 fallback 文案描述「首个 Tauri 2 版本发布，从 Electron 迁移完成」，而本产品是 Electron 43 —— 两个产品线的口径混入。

### 多角度论证
- **为什么要改**：下载页是用户获取产品的第一入口，404 = 流量全损；release notes 展示另一个产品的更新日志 = 品牌混淆。这是全部发现里唯一「用户一定看得见」的事故。
- **不改会怎样**：每次发版都要手抄 5 个链接，发一次错一次（本次 v3.2.0 就是手抄事故的实证）。
- **替代方案对比**：① 全静态硬编码新版本号——零工作量但重蹈覆辙；② **动态解析 GitHub API latest release（推荐）**——零维护，永远指对；③ 构建期注入——需要给官网加构建链，当前官网是无构建静态站，成本不成比例。选②。

### 具体改法

**第一步：修 download.js 仓库与动态化。**
```js
// site-build/js/download.js
const REPO_OWNER = '232252';
const REPO_NAME = 'education-advisor';   // ← 从 'education-advisor-tauri' 改正

// 页面加载时拉 latest release，把资产名映射到按钮：
async function bindDownloadButtons() {
  const res = await fetch(`https://api.github.com/repos/${REPO_OWNER}/${REPO_NAME}/releases/latest`);
  if (!res.ok) return;                    // 失败时保留 HTML 内的静态兜底链接
  const release = await res.json();
  const assetByName = (pred) => release.assets.find(pred);
  const bind = (id, pred) => {
    const a = document.getElementById(id);
    const asset = assetByName(pred);
    if (a && asset) a.href = asset.browser_download_url;
  };
  bind('dl-win-setup',  a => /Setup\.exe$/.test(a.name));
  bind('dl-win-portable', a => /Portable\.exe$/.test(a.name));
  bind('dl-mac-arm',    a => /arm64\.dmg$/.test(a.name));
  bind('dl-mac-x64',    a => /x64\.dmg$/.test(a.name));
  bind('dl-linux-deb',  a => /\.deb$/.test(a.name));
}
```
**第二步：download.html 按钮**加 `id`（如上），`href` 兜底值改为当前已发布的真实 tag（发布 v0.1.0 后更新一次，此后不再动）。
**第三步**：Release Notes 的 fallback 文案改为与本产品一致的通用文案（去掉 Tauri 迁移叙述）。

### 预期效果
下载按钮永远指向最新 release 的真实资产；Release Notes 显示本产品更新日志。

### 验证方法
本地 `python3 -m http.server -d site-build` 打开 download.html：断网/改 hosts 模拟 API 失败时兜底链接可达；正常时按钮 href 被替换为 api.github.com 返回的 browser_download_url。

### 回滚方案
纯前端静态文件，`git revert` 即可，无数据影响。

### 风险评估
低。GitHub API 匿名额限 60 次/小时/IP，对低流量官网足够；失败路径已有静态兜底。

## R2-02 修复 2 处工具声明断链 + 建立 lint 防回归

### 定位
- `agents/main/AGENTS.md:21` 声明 `eaa_revert_event`，但 `config/agents.yaml:32-43` main 的 capabilities 无 `revert`
- `agents/discipline-officer/AGENTS.md:11,33` 声明 `eaa_revert_event` 与 `eaa_add_student`，`agents.yaml:415-422` 两者皆无
- 工具映射表 `src/main/services/eaa/tools/registry.ts:79`（`revert: [revertEventTool]`）与 `:78`（`add_student`）本身存在，只差 capability 授权

### 现状证据（已逐行核实）
main capabilities 实为 `read/summary/add_event/add_student/history/search/list/ranking/stats/codes/range` —— 无 revert；discipline-officer 实为 `read/add_event/search/list/ranking/summary/history` —— 无 revert、无 add_student。（`agents/safety/AGENTS.md:27` 已正确声明「撤销不在本角色工具集内」，无需处理。）

### 多角度论证
- **为什么要改**：提示词是模型的行为契约。AGENTS.md 教模型「撤销走 eaa_revert_event」，模型会尝试调用，运行时却发现工具不存在——轻则模型道歉改道（浪费一轮），重则模型自行「变通」用加分事件对冲扣分（discipline-officer 的 AGENTS.md:11 明令禁止这种对冲，但工具缺失时模型可能明知故犯）。**这是「AI 说谎」问题，直接损害可信度。**
- **为什么选「补 capability」而不是「删提示词」**：main 是主协调者，教师最常用的撤销场景（「刚才那条记错了，撤销」）理应 main 直接处理而非强制委托；discipline-officer 的职责就是纪律处分管理，撤销错误处分是其分内事。删提示词会让这两个角色在真实需求面前无能为力。
- **替代方案**：把撤销集中在 executor（系统维护角色）——但教师心智模型里「谁记的谁撤」更自然，且 delegate 一轮多一次 LLM 调用成本。否决。
- **权限安全论证**：revert 是写操作，但 agents.yaml 注释已声明「工具实际执行时仍由工具内部校验权限，这里只是声明意图」，且 `_shared/rules.md` 要求写操作先确认。给这两个角色补 revert 的风险与已有的 add_event 同级，可接受。

### 具体改法

**第一步：agents.yaml 补 capability**
```yaml
# main（agents.yaml:32-43 的 capabilities 列表追加）
    capabilities:
      # ...现有 11 项保持不变...
      - revert          # ← 新增：主协调者直接处理「记错了，撤销」场景

# discipline-officer（agents.yaml:415-422 追加）
    capabilities:
      # ...现有 7 项保持不变...
      - revert          # ← 新增
      - add_student     # ← 新增：违纪学生若未入库需先建档
```

**第二步：防回归——扩展 `scripts/prompt-lint.mjs`**。新增一条检查：解析每个 agent 的 AGENTS.md 工具表格（`| \`eaa_xxx\` |` 行），提取工具名；对照 agents.yaml 的 capabilities 经 registry.ts 映射展开后的实际工具集；**声明 ⊄ 实际**即报错。这样本次这类断链以后在 CI 就被拦住，不依赖人工对齐。
（实现提示：registry.ts 的 cap→tools 映射是 TS 文件，lint 脚本可用简单正则提取该映射表的键值对，或在 `src/main/services/agent/config.ts` 中导出一份 JSON 快照供 lint 消费。）

### 预期效果
main 与 discipline-officer 可真实执行撤销；未来任何「提示词声明了未授权工具」在 CI 被拦截。

### 验证方法
1. `npm run prompt:lint` 通过（含新检查）；
2. 启动应用 → Chat 选 main → 输入「撤销张三刚才那条迟到记录」→ 观察 ToolCallRow 出现 `eaa_revert_event` 且成功；
3. 故意在某个 AGENTS.md 写一个不存在的工具名，确认 lint 报错。

### 回滚方案
agents.yaml 单文件 revert；lint 新检查独立成函数，可单独关闭。

### 风险评估
低。capability 放宽仅影响这两个 agent；写操作仍有「先确认」规则与工具内部校验双重约束。

## R2-03 死配置清理（「可配但不生效」的假象）

### 定位与现状证据
| 项 | 位置 | 证据 |
|---|---|---|
| `advanced.shellPath` / `advanced.sessionDir` / `advanced.httpIdleTimeoutMs` | `src/shared/types/settings.ts` + `config/default-settings.json` | 全仓唯一定义点，无任何读写方 |
| `general.defaultOperator` | types/settings.ts | 仅类型出现，无消费端 |
| `general.telemetry` | types + settings-handlers 白名单透传 | 无采集端 |
| `models.maxConcurrentCronTasks` | types + 设置 UI | cron-service 不读取 |
| 根目录 `settings.json` | 仓库根 | 无代码读取（运行时配置在 userData/settings.json，`settings-service.ts:38`）；与 config/default-settings.json 漂移（defaultOperator ""/"班主任"） |
| `general.dataDir` | settings-service 写入 + Dashboard 显示 | 数据层不消费——**此项不在本批处理，并入 R2-17 path-resolver 统一时真正接线** |

### 多角度论证
- **为什么要改**：目标用户是非 IT 教师。设置页里一个可编辑但不生效的开关，比没有这个开关更糟——用户改了 `maxConcurrentCronTasks` 以为生效了，实际没有，这是对信任的透支。根 settings.json 则会误导开发者（两个「默认配置」打架）。
- **逐项取舍论证**：
  - `advanced.*` 三项：纯死，直接删（types + defaults + 若设置 UI 有对应输入框一并删）；
  - `defaultOperator`：删除（无消费场景）；
  - `telemetry`：本项目主打隐私优先、无采集后端，保留这个字段反而引人误会，删；若未来做匿名统计再设计完整的采集-展示链路；
  - `maxConcurrentCronTasks`：**不删，接线**——cron 任务并发限流有真实价值（19 条 cron 若同时触发会并发压 LLM API，当天的 429 配额错误就是并发压力的实证）。接线只需 cron-service 调度处读取设置。
  - 根 settings.json：删除（历史遗留，git 历史里留档即可）。

### 具体改法
1. `src/shared/types/settings.ts`：删除 `advanced` 命名空间下三个字段、`defaultOperator`、`telemetry` 的类型声明；
2. `config/default-settings.json`：同步删除对应键；
3. 设置页（`src/renderer/pages/Settings/`）若渲染了这些字段，删除对应输入控件；`settings-handlers.ts` 白名单同步收紧；
4. **接线 maxConcurrentCronTasks**：`src/main/services/cron-service.ts` 任务调度入口处（注册/触发执行的位置）加信号量限流：
   ```ts
   const max = settingsService.getSettings().models.maxConcurrentCronTasks ?? 2;
   // 简易信号量：正在执行的 cron 任务数达到 max 时，新任务排队等待（复用现有 runQueue 的串行模式即可）
   ```
5. `git rm settings.json`（根目录）。

### 预期效果
设置页每个可见配置都真实生效；开发者不再被两个「默认配置」误导。

### 验证方法
`grep -rn "shellPath\|sessionDir\|httpIdleTimeoutMs\|defaultOperator\|telemetry" src/ config/` 零残留；全量回归基线通过；手动把 maxConcurrentCronTasks 设为 1，触发两条同刻 cron，确认第二条排队。

### 回滚方案
git revert；无数据迁移。

### 风险评估
低。唯一注意点：已存在的用户 userData/settings.json 里可能存有这些键——读取时未知键应被忽略（确认 settings-service 合并逻辑对未知键宽容；若严格校验则需迁移清洗一步）。

## R2-04 Git 推送与工作区残留清理

### 定位与现状证据
- `main` 领先 `origin/main` 5 个提交（含 f6e8d36 AI↔业务联动大修），0 落后——**GitHub/Gitee 上缺最新代码**；
- 未跟踪脏物：`.trae-tmp/`（root 属主，196K）、`site-build/prod-light.png`（617K，无引用）；

- root 属主残留：`site-build/`、`electron-builder.yml`、`.trae-tmp/`、`promo/` 部分文件（本机 sudo 不可用）。

### 多角度论证
- **为什么先推送**：5 个未推送提交里包含全部 AI 联动修复——不推送则：① Gitee 镜像工作流（依赖 GitHub release）全部滞后；② 本地磁盘是唯一副本，任何意外即丢失 1751 行修复。**这是当前最大的数据风险，且修复成本为零。**
- 残留文件为什么清：.trae-tmp 是其他工具的临时产物，混在工作区污染 git status；prod-light.png 是构建快照残片。

### 具体改法
```bash
git push origin main            # GitHub
git push gitee main 2>/dev/null || true   # Gitee 若有直推分支也同步；其 release 镜像由 CI 负责
rm -rf node_modules.broken.bak  # admina 属主，可直接删
```
- `.trae-tmp/`：内容为 root 属主且目录权限 `dr-sr-x--`，本机无 sudo 无法删内部文件——**可从仓库根直接改名挪走**（对目录条目的 rename 只需父目录写权限，仓库根是 admina 可写）：`mv .trae-tmp .trae-tmp.deleted-root-owned && echo "待有 sudo 环境时 rm -rf"`；或等有 sudo 的时机一次性 `sudo rm -rf .trae-tmp`。二选一，别留在 git status 里。
- `site-build/prod-light.png`：位于 root 属主目录 `site-build/`（`dr-sr-x--`）内，同样无法直接删——把它加入 `.gitignore`（`site-build/prod-light.png` 或 `site-build/*.png` 按需）以消除 status 噪音，文件本体等 sudo 时机删。
- `electron-builder.yml`/`site-build/` root 属主问题：属主不影响 git 操作（git 只读写 .git），**不必修复属主**，只需知道「删除其中文件需要 sudo」这一事实即可。把此注意事项记入 docs/DEVELOPMENT.md 环境一节。

### 预期效果
远端与本地一致；`git status` 干净；本地磁盘减少约 240M 需另行清理的垃圾目录登记（promo/resources/intro 的物理清理见 R2-24）。

`git status -sb` 显示 `## main...origin/main` 无 ahead；`git log origin/main..main` 为空。

### 回滚方案
推送不可回滚（可 revert 提交）；清理项均在 .gitignore/本地文件层，无代码影响。

### 风险评估
推送前确认 CI（三 OS 矩阵）在远端跑绿——本地全绿是已知状态，远端 Linux runner 曾有历史阻塞（见 463a502/ed14d45 修复），推送后盯一眼 Actions。

# 第二批 R2-B：AI↔业务联动补强（预计 2-4 天，本轮灵魂）

## R2-05 班级元数据注入 system prompt（「懂业务」→「懂你的班」）

### 定位
- 注入装配点：`src/main/services/agent/system-prompt.ts:45-83`（buildSystemPrompt）+ `src/main/services/agent/execution.ts:138-150`（调用处）
- 数据源：SQLite `classes` 表（`db/schema.ts:11-85`，经 `class-service.ts:157` 读写），学生数可从 EAA `list-students` 缓存取

### 现状证据
当前 system prompt 十段（SOUL/项目背景/Skills/公共规则/角色规则/长期记忆/风险阈值/运行环境/工作准则/对话设置）中**没有任何一段是「本班基本信息」**：年级、班级名、学生数、科目构成、学期范围全部缺席。教师问「我们班最近怎么样」，模型只能现查工具或泛泛而谈。

### 多角度论证
- **为什么要改**：这是 7→8.5 分路径上性价比最高的一项。数据已在库里（零新采集），注入是纯 prompt 拼装（零新依赖），效果立竿见影——模型开场就知道「高二(3)班，48 人，语数英+理综，本学期 9 月-1 月」，所有后续问答的上下文锚点就建立了。
- **为什么不做成工具而不注入**：曾考虑加 `eaa_class_info` 工具让模型按需查。否决理由：① 班级元数据是几乎每轮对话都需要的背景，做成工具等于每轮多一次 LLM↔工具往返（延迟+成本）；② 模型「需要想到去查」本身就是失败模式（R1 审计已确认此类问题）。静态注入 + 数据变化时刷新是正确形态。
- **注入多大才不会撑爆 prompt**：班级元数据 < 200 字符，相对现有 prompt 体量（project-context 31 行 + 规则 + 记忆 4000 字符上限）完全无感。
- **多班教师怎么办**：当前产品形态是单班主任单班（classes 表支持多班但 UI 主线是单班）。设计上做成「当前活跃班」概念：取 classes 表第一条 enabled 班级或最近有事件写入的班级；若未来多班，此段改为按会话选择的班级注入，接口不变。

### 具体改法

**第一步：`system-prompt.ts` 新增构建函数**
```ts
// src/main/services/agent/system-prompt.ts
export interface ClassContextInfo {
  className: string;      // 例：高二(3)班
  grade?: string;         // 例：高二
  studentCount: number;
  subjects?: string[];    // 例：语文/数学/英语/物理/化学/生物
  term?: string;          // 例：2026-2027 学年第一学期
}

export function buildClassContextSection(info: ClassContextInfo): string {
  return [
    '## 当前班级',
    `- 班级：${info.className}`,
    `- 学生人数：${info.studentCount}`,
    info.subjects?.length ? `- 科目构成：${info.subjects.join('、')}` : null,
    info.term ? `- 学期：${info.term}` : null,
    '- 回答「我们班」相关问题时以此班级为准；人数等统计仍应经工具实时核实。',
  ].filter(Boolean).join('\n');
}
```

## R2-07 封堵脱敏旁路：file/excel/MCP 工具纳入 privacy-guard 包装

### 定位
- 包装点：`src/main/services/agent/tools.ts:74` —— `const eaaTools = privacyGuard ? rawEaaTools.map((t) => privacyGuard.wrapTool(t)) : rawEaaTools`（**仅 EAA 工具被包装**）
- 包装器：`src/main/services/agent/privacy-guard.ts:149-185` wrapTool（入参 deanonymize / 结果 anonymize，双向）
- 旁路工具：file-tools（read_file/read_excel/write_file/list_dir）、utility-tools、MCP 工具

### 现状证据
privacy-guard 头注释自认「非 EAA 工具不包装」。开启 autoAnonymize 后，agent 执行 `read_excel("成绩表.xlsx")` → Excel 里的真名原样进入模型上下文——**用户以为开着脱敏就安全，实际一个文件读取就绕过了**。这是「隐私优先」核心卖点上的一道裂缝。

### 多角度论证
- **为什么必须修**：README/PRIVACY_ENGINE.md 宣传隐私优先，脱敏旁路存在意味着承诺可被一次 `read_file` 击穿。审计角度这是严重级；产品角度这是差异化卖点的事故隐患。
- **为什么 wrapTool 语义正好适用**：file 工具的风险方向与 EAA 工具一致——**结果（文件内容）出域前需要 anonymize（真名→S_001），入参（模型写的文件路径/内容）回域需要 deanonymize**。wrapTool 已实现这两个方向，理论上直接套用。
- **替代方案对比**：① 路径白名单（脱敏开启时只允许读白名单目录）——一刀切，agent 读自己写的周报文件也会被拦，伤功能；② **全面 wrapTool 包装（推荐）**——语义连续、代码复用现有包装器；③ 出域前全文过滤（在 streamFn 层做）——粒度太粗，工具结果与模型输入的边界会混乱。选②。
- **注意一个不对称**：EAA 工具的 deanonymize 入参是为了「模型用化名查数据」；file 工具的 deanonymize 入参还承担「模型把化名写回文件」的场景（例如 agent 生成报告含 S_001，教师要导出真名版）——此时应该 deanonymize 写入内容吗？**不应该**：写文件是本地落盘，真名留在本地是安全的且更符合教师预期。**所以 file 工具只包装 read 方向**（read_file/read_excel/list_dir 的结果 anonymize），write 方向不包装。这是与 EAA 工具的关键差异，实现时注意。

### 具体改法
```ts
// src/main/services/agent/tools.ts（:74 附近扩展）
const eaaTools = privacyGuard ? rawEaaTools.map((t) => privacyGuard.wrapTool(t)) : rawEaaTools;

// R2-07: 只读类文件工具同样包装（结果 anonymize）；写类工具不包装（本地落盘保留真名）
const READ_SIDE_FILE_TOOLS = new Set(['read_file', 'read_excel', 'list_dir']);
const fileTools = privacyGuard
  ? rawFileTools.map((t) => (READ_SIDE_FILE_TOOLS.has(t.name) ? privacyGuard.wrapTool(t) : t))
  : rawFileTools;
```
（若 wrapTool 对非 EAA 工具的结果对象形态有假设——f6e8d36 曾修复「wrapTool 对 AgentToolResult 对象形态的处理」——为 file 工具的结果结构补一条单测确认兼容。）

**MCP 工具**：`mcp.yaml servers: []` 当前为空，属 dormant。在 MCP 工具注册处（tools.ts 中 MCP 分支）加同款包装（read 类语义不明，默认对**全部** MCP 工具结果做 anonymize——MCP 是外部扩展，宁可过保护），并加注释「MCP 工具结果一律过脱敏」。

**配套**：新增测试 `tests/main/agent-privacy-file-tools.test.ts`：
1. 构造含「张三」的临时文件 → 开脱敏运行 agent 调 read_file → 断言模型上下文中只出现 S_001 化名；
2. write_file 写入含 S_001 的内容 → 断言落盘文件保留 S_001（不 deanonymize，本地方向）；
3. 脱敏引擎未解锁时 read_file 走 fail-closed（复用 privacy-guard.ts:35-41 的既有行为）。

### 预期效果
脱敏开启后，真名进入模型的途径只剩「用户自己输入的原话」（这本来就是脱敏管的，execution.ts:347 已处理）。旁路闭环。

### 验证方法
新增测试全绿 + 手动：开 autoAnonymize → 让 agent 读含真名的 Excel → 在 ToolCallRow 展开的工具结果里确认化名。

### 回滚方案
包装开关在 tools.ts 一处，revert 即回到只包 EAA。

### 风险评估
中低。read_excel 解析出的多维结构（单元格/表头）经过 anonymize 的正则替换需保证不破坏结构——现有 anonymize 是文本替换，对字符串单元格安全；测试覆盖即可。

## R2-10 修复大小模型分流（model_tier 名存实亡）

### 定位
- `src/main/services/agent-model-selector.ts:62-66`：`let modelId = settings.models.defaultModel; if (!modelId) { modelId = tier === 'high_quality' ? highQualityModel : lowCostModel }`

### 现状证据
defaultModel 优先级最高：用户在 Models 页设过默认模型后，`selectModel('high_quality')` 与 `selectModel('low_cost')` 返回**同一个模型**。agents.yaml 里逐 agent 标注的 model_tier（main=high_quality、discipline-officer=low_cost 等 18 处）全部失效。代码注释自述动机「using defaultModel first to inherit user's selected model contextWindow」——为继承 contextWindow 而牺牲了分层语义。

### 多角度论证
- **为什么要改**：分层的业务价值是真实的：周报/学情分析要质量（贵模型），纪律扣分确认/定时巡检要成本（便宜模型）。19 条 cron 全部跑 defaultModel 的话，要么全贵要么全便宜。当前实现等于把分层决策权从「逐 agent 配置」收窄为「全局一刀切」。
- **修复方向论证**：改为「tier 专属模型优先，defaultModel 兜底」：
  - `tier 专属已配置（highQualityModel / lowCostModel 非空）→ 用之`；
  - `未配置 → defaultModel`；
  - `都没有 → 现有五级降级链`。

### 多角度论证
- **为什么统一而不是各自修**：给 academic 补 dev 重定向只是把 4 套变 5 套。根因是「dev/prod 判定 + 根路径」没有单一事实源。一个 `paths.ts` 模块一次性烧掉全部特例。
- **目标布局论证**：
  ```
  dev:  <root>/.app-data/{workstation.db, academics/, profiles/, skills/, memory/}
        <root>/.eaa-data/            ← 仅 Rust CLI 领地（entities/events/privacy）
  prod: <userData>/{workstation.db, academics/, profiles/, skills/, memory/}
        <userData>/eaa-data/         ← 仅 Rust CLI 领地
  ```

- **迁移论证**：academics/profiles 现存两处副本（R154 迁移带过去的旧副本 + 此后写入的 userData 副本）。resolver 落地时做一次性迁移：若旧位置 `userData/eaa-data/academics` 存在且新位置不存在 → move；`<root>/.eaa-data/academics` 旧副本直接废弃（.eaa-data 已 gitignore，无入库风险）。迁移逻辑放 resolver 初始化，幂等。
- **dataDir 设置接线**（R2-03 遗留）：`settings.general.dataDir` 在 resolver 内生效——非空绝对路径时作为 `.app-data` 与 eaa-data 的共同父目录。这样该设置从死配置变为真功能（教师把数据放到 D 盘等场景），且只有一处消费点。

### 具体改法
1. 新建 `src/main/services/paths.ts`：

     appDataDir: string;      // .app-data / userData

     academicsDir: string;    // appDataDir/academics
     profilesDir: string;     // appDataDir/profiles

   export function resolveAppPaths(): AppPaths   // 单例缓存；启动时执行一次迁移

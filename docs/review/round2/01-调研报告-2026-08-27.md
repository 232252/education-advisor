## 三、模块化审计（用户问题：「哪些该模块、哪些不该、该拆该合、过程对不对」）

### 3.1 主进程结构（src/main，约 2.3 万行 + preload 19 文件）

实测：544 文件 import 图 **0 循环依赖**；137 个 IPC 通道常量单点定义于 `src/shared/ipc-channels.ts`，与 128 个 handler、128 个 preload invoke 全对账（`npm run ipc:contract` PASS）。

**模块化做得对的（应保持）：**
- 「`x-service.ts` 薄编排层 + 同名子目录放实现」范式全仓一致（eaa-bridge→`eaa/`、db-service→`db/`、cron-service→`cron/`、agent-service→`agent/`），公共 API 稳定、子模块可测；
- IPC 按域分层（`ipc/<domain>/{handlers,params,cache}.ts`），缓存上下文注入复用；
- bridge 与 ipc 解耦用回调钩子而非反向 import（`eaa-bridge.ts:88-102`），是避免环的正确做法；
- scripts/ 长期脚本全部接入 npm scripts/CI，一次性脚本归档 `scripts/archive/`（16 个 + README），分离纪律好。

**模块化做错的（本轮新认定）：**
- **[严重] 数据目录解析 4 套并行实现且互不一致**——这是本轮最大的架构发现：
  | 实现 | 位置 | dev 模式行为 |
  |---|---|---|
  | EAA 桥 | `eaa/legacy-migration.ts:75-110` resolveDataDir | 重定向到 `<项目根>/.eaa-data` |
  | SQLite | `db/connection.ts:22-56` | 重定向到 `<项目根>/.app-data` |
  | 学业成绩 | `academic-service.ts:54` | **硬编码 `userData/eaa-data/academics`，无重定向** |
  | 学生档案 | `profile-service.ts:17` | **硬编码 `userData/eaa-data/profiles`，无重定向** |
  另有 `skill-service.ts:29-32`、`memory-service.ts:47` 各选了第三、四种位置约定。后果：开发模式下学业数据写入 A、EAA 数据读写 B，两套视图分裂；学业/档案数据混入 Rust CLI 领地（`doctor --fix` 可合法触碰）；备份走 `getDataDir()` 会打包到旧副本。
- [中等] `agent-service.ts`(555 行)同时管配置加载、SOUL 读写、调度接线、运行队列、委托桥接、上报桥接 6 类职责，与 `agent/execution.ts`(515 行)形成「两个半层」；
- [中等] ipc 层两套组织标准并存：ai/eaa/class/academic/privacy/students 有子目录，sys(251)/settings(214)/feishu(196)/cron(193) 是单文件平铺；
- [中等] 飞书实现分散三处（`feishu/`、`feishu-bot/`、`feishu-bot-service.ts` 426 行），新人无法回答「飞书的代码在哪」；
- [中等] 绕过常量表的私有通道 `'__invalidate_students_cache'`（`ipc/eaa/handlers-system.ts:311,333`）用全局 EventEmitter 做模块内调用，靠 `__invalidateListenerRegistered` 守卫补救；
- [轻微] 8 行文件 `ipc/ai/state.ts`、纯 re-export 的 `ipc/class/params.ts` 属过度拆分边缘（作为 test seam 尚可接受）。

**该拆清单**：① agent-service → agent-config-service + run-controller；② eaa-bridge.execute() 内 4 种横切策略（缓存/序号/重试/队列）→ policy pipeline；③ **统一 path-resolver 单例**（烧掉 6 处各自解析）——优先级最高。
**该合清单**：① feishu 三棵树合并为单棵领域树；② `ipc/ai/state.ts` 并入 chat-handlers；③ 根目录 `settings.json` 死文件删除；④ `command-classification.ts` 幽灵命令名（list/get/query/report/find/show/status 等不存在的命令）与 WRITE_COMMANDS 合并为单一命令元数据表。

### 3.2 渲染层结构（src/renderer，约 270 文件 3.4 万行）

## 五、AI↔业务联动专项（用户核心关切）

### 5.1 AI 对话时到底「懂」多少？（安装后开箱即问「我这个项目/班怎么样」，能答多全）

**打分：7 / 10。** 拆解：

**懂的（得分点）：**
1. **业务世界观完整注入**：每个 agent 的 system prompt 由 `system-prompt.ts:45-83 buildSystemPrompt` 拼装 = SOUL(人格) + project-context(项目背景 31 行：操行分/事件溯源/原因码 LATE -10 示例/统一风险分级 <85/85-93/≥100/六科加权 语数英1.5/18-agent 名册) + Skills 段 + 公共规则 + 角色规则 + 长期记忆 + 风险阈值行 + 运行环境。「AI 知道自己运行在整个系统的什么位置」——f6e8d36 修复后此问题已解决；
2. **数据实时可达**：15 个 EAA 工具（eaa_score/ranking/stats/codes/history/search…），配合「没查到的数据就是不存在」铁律（project-context 明示），查分/统计/加减分问答专业且有据；
3. **主链路当天仍在真实成功**（见 §四运行证据）。

**不懂的（扣分点）：**
1. **[中等] 班级静态元数据盲区**：不知道用户带的是几年级、什么班、多少人、考哪几科——classes 表在 SQLite 里存在但没有做成注入或工具。「我们班情况怎么样」这类开放问题容易答得泛；
2. **[中等] 路由靠人选**：Chat 页用户手动选 agent（默认第一个 enabled 即 main），无意图识别——选错 agent 就答非所问，理解成本转嫁给教师；main 的 delegate_to 是唯一动态路由；
3. **[中等] 记忆/技能空转**：记忆代码完备但 `.app-data/memory/` 不存在（零真实沉淀，功能上线不足一天）；技能库仅 1 个文件（STUDENT_MANAGEMENT.md，且与 rules/project-context 内容大量重复），`.app-data/skills/` 为空；
4. **[中等] 大小模型分流失效**：`agent-model-selector.ts:62-66` defaultModel 优先级压倒 tier——用户设过默认模型后，yaml 里逐 agent 标注的 model_tier（main=high_quality、discipline-officer=low_cost 等）选出的是**同一个模型**，分层名存实亡。

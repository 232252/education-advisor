# Education Advisor 全面调研报告

> 基线：v0.1.0-rc.1（M1-M11 改造完成后复审）
> 审计方法：4 路并行深度扫描（主进程模块化 / 渲染层 UI / 端到端链路 / 复用与臃肿）+ 人工二次核实关键发现
> 代码规模：src 非测试代码 521 文件 / 约 51,475 行；测试 159 文件 / 约 2,575 用例；Rust eaa-cli 约 4,379 行
> 日期：2026-08-19

---

## 一、总体结论

**架构骨架是健康的，债务集中在四个层面**：

| 层面 | 总评 | 一句话结论 |
|---|---|---|
| 模块化结构 | ★★★★☆ | "门面单文件 + 领域子目录"双层结构自洽；5 个大文件该拆，ipc/ 层三种组织风格并存 |
| 端到端链路 | ★★★★☆ | 四层 IPC 对齐纪律极强（契约测试 PASS：130 常量/123 handle/123 invoke 全对齐）；但 3 处"类型撒谎"+ 1 处缓存竞态 |
| 渲染层 | ★★★☆☆ | 分层纪律好（页面=编排+hooks+components+lib）；但基础设施"造了没换上"：Button 采用率 2.9%、i18n 44% 文案绕过 |
| 提示词/资产层 | ★★☆☆☆ | **最大意外发现**：8/18 份 AGENTS.md 逐字节相同且为 OpenClaw 模板残留；主 agent SOUL.md 是 0 字节；约 230MB 视频素材在 git 内 |

工程纪律反常严格（CI 三 OS 矩阵 + 契约测试 + doc 漂移检查 + 覆盖率门禁 + CodeQL），历史修复痕迹密集（R87/H-3/F3/P1-36/R151 等注释）。**这不是一个烂摊子，而是一个底子很好、带着三个历史时代残留（CLI 时代、OpenClaw 服务器时代、宣传视频制作期）的项目。**

## 二、模块化正确性审计（主进程）

### 2.1 该模块 / 不该模块 —— 判定清单

**22 个单文件服务中只有 4 个是纯转发 shim**，其余 18 个是真实实现（门面/编排层）：

| 判定 | 文件 | 证据 |
|---|---|---|
| 🔴 不该独立存在 | `services/mcp-tools.ts`（22 行） | 纯 re-export `mcp-management/tools/`，唯一生产消费者是 `agent/tools.ts` 一处 import |
| 🟡 保留合理 | `eaa-tools.ts`(28行)、`file-tools.ts`(32行)、`feishu-service.ts`(22行) | 实为 barrel 桶文件：12 处测试导入经它们进入，删除需改 12 处测试，代价收益不划算 |
| 🟢 判定正确 | 其余 18 个真实实现 | eaa-cache.ts 的 TtlLruCache 被 ipc 层 7 处复用，是抽离正确范本 |

**结论：模块化"过程"基本正确**。M1-M11 的拆分（eaa/、cron/、db/、feishu-bot/ 等子目录）方向对、粒度合理；唯一下探过度的只有 4 个 20 行级转发文件（见上表）。

### 2.2 该拆没拆 —— 5 个大文件

| 文件 | 行数 | 混杂职责数 | 核心问题 |
|---|---|---|---|
| `agent/execution.ts` | 603 | 8 类 | 单函数 executeAgentRun 约 560 行：prompt 模板拼接(35行硬编码) + 压缩预检查(与 compaction-helper 三处重复) + 事件 switch(90行) + 续跑循环 + 落库 + 清理 |
| `eaa-bridge.ts` | 466 | 5 类 | **4 个复制粘贴的重试块**：读分支与写分支的 os error 5 重试、空 stdout 重试逐字相同 |
| `agent-service.ts` | 462 | 4 类 | 目录探测 + 配置 CRUD（updateAgent patch 校验 40 行属 agent/config.ts 域）+ prompt 读写壳 + 执行编排 |
| `feishu-bot-service.ts` | 429 | 4 类 | start 单方法 135 行（含 50 行 SDK 配置细节）+ 守护重启 + 休眠唤醒 + 状态机 |
| `pi-ai/streaming.ts` | 400 | 7 类 | 单 generator 360 行：设置解析 + abort 管理 + 消息互转胶水 + 重试循环 |

### 2.3 该合没合

- `feishu-bot-service.ts:429` 反向导出 `getErrorMessage from './eaa-bridge'`——feishu-bot 域转发 eaa 域导出，职责泄漏。
- `services/` 顶层"单文件门面 + 子目录"双轨本身自洽（门面持状态、子目录放纯逻辑），**不建议强行合并**。

### 2.4 ipc/ 层组织不一致（三种风格并存）

| 风格 | 域 | 现状 |
|---|---|---|
| cache+params+分组 handlers | academic、eaa | eaa/commands.ts 150 行里混了参数组装（应进 params）和缓存预热（应进 cache） |
| 仅分组 handlers | ai、privacy | privacy/params.ts 66 行**自实现校验完全未复用 utils/sanitize**（平行实现） |
| params 是 8 行纯转发 | class | 与 academic/params.ts(13行包装)、privacy/params.ts(66行自实现) 三种"params"语义漂移 |

**拆分阈值颠倒**：sys(219行)/settings(205行)/feishu(196行)/cron(192行)/agent(189行) 均大于 academic 域总量却未拆子目录，而 academic 拆了 5 个文件。

**测试绑架结构**：`eaa-handlers.ts`(170行) 保留 2 个本地 handler 的唯一原因是 tests/e2e 源码断言依赖 `studentsCache/rankingCache` 标识符出现在该文件中——测试断言反向锁死了文件结构。

### 2.5 utils 收敢单点

| 工具 | 引用 | 漂移点 |
|---|---|---|
| logger（facade over log/） | 23 处 | **零漂移，全项目最佳样板** |
| utils/sanitize | 9 处 | `ipc/privacy/params.ts` 66 行平行实现；`profile-handlers.ts` 本地变体（有差异注释，属有意保留） |
| utils/atomic-write | 4 处 | `keystore-service.ts:100-108`、`settings/persistence.ts` 各自手写同一套 fd+fsync+rename 序列 |

## 三、渲染层 UI 审计

### 3.1 路由与布局

- `App.tsx`(106行)：12 页面全部 lazy 代码分割 + ErrorBoundary + 兜底重定向 —— **无问题**。
- `MainLayout.tsx`(301行)：**约 90 行非布局逻辑**——数据引导(fetchAgents/initStatusListener)、通知监听、全局快捷键、Agent 状态派生全混在布局组件里。且 ChatPage:59 与 MainLayout:58 **重复调用 fetchAgents()**。

### 3.2 组件复用率（分母 137 个页面 tsx）

| 组件 | 采用率 | 判定 |
|---|---|---|
| EmptyState | 27%（37 文件） | ✅ 最佳 |
| Card | 24%（33 文件） | ✅ 良好 |

### 3.3 跨域重复组件（4 组实证）

### 3.4 i18n 双轨制

- 字典层 ✅：zh/en 各 836 key 完全对齐，有测试强制保障。
- 源码层 🔴：**≥438 处硬编码中文**（JSX 属性 202 处 + 文本节点 192 处 + toast 44 处）vs 552 处 t() 调用——**约 44% 用户可见文案绕过 i18n**。WelcomePage 是 0 个 t() 的全硬编码页面。

### 3.5 状态管理

- agent/（7 文件 470 行）与 chat/（9 文件 749 行）slice 切分合理，status-slice 的订阅总线 + OPT-4 跳过未变化推送是亮点。

- `useAsync` hook **0 个页面消费者（死代码）**；全项目竞态保护有 4 种写法（cancelled 旗标/mountedRef/reqId+mounted/token）。

## 四、端到端链路审计

### 4.1 契约层 ✅

`node scripts/ipc-contract-test.mjs --static` **PASS**：130 通道常量、123 个 ipcMain.handle、123 个 preload invoke，P⊆H 且 H=P。7 个"仅常量"通道均为主→渲染推送（webContents.send），设计合理。

死链仅 3 处：`agent.getHistory`（preload 暴露但渲染层零调用）、`feishu.status`、`sys.getPath`（半死链，诊断用途）。

### 4.2 类型撒谎（错误路径返回形状与契约不符）

| 通道 | 声明类型 | catch 实际返回 | 后果 |
|---|---|---|---|
| **`cron:list`** | `CronTask[]` | `{success:false, error, tasks:[]}` 对象 | **service 抛错时渲染层 `.map()` 直接 TypeError 白屏**（已人工核实 cron-handlers.ts:32） |
| `agent:get` | `AgentDetail \| null` | `{success:false, error}` | 形状完全不符 |
| `skill:get` | `Skill \| null` | `{success:false, error}` | 同上 |

模式性结论：F3 修复了 cron:get-logs 等处但漏了这 3 处——**同类错误处理不一致**是系统性问题。

### 4.3 EAA 子进程链路

| 发现 | 位置 | 严重度 |
|---|---|---|
| **读写竞态缓存污染**：读命令在途时写命令插队（写 clear 先于读 set），读完成后把**写前旧数据写回缓存驻留 10s** | eaa-bridge.ts:262-306 | 中 |
| abort/溢出路径只发 SIGTERM 无 SIGKILL 升级（超时路径有双段击杀），可产生孤儿进程 | process-executor.ts:92-100,142,156 | 中 |
| eaa:import 大文件无专属超时，默认 30s 误杀 | handlers-export.ts:78 | 低 |
| ReadCache 超 64 条全清而非 LRU 逐条淘汰 | binary-discovery.ts:60 | 低 |

健壮面：stdout 50MB 上限 + 中文多字节正确处理、os error 5 与空 stdout 重试、ENOENT 自动重探测、错误结构化传到 UI 并翻译——质量良好。

### 4.4 Agent 执行链路

时序完整（runManual → runAgent → runQueue(代数+maxDepth=8) → executeAgentRun → 事件订阅逐 delta 推送 → waitForIdle(5min) → 续跑循环 → 落库 → idle 推送）。abort 传播链（generation + signal + finally 兜底）质量良好。

薄弱点：waitForIdle 5min 硬上限误杀长任务且**超时错标为 error 而非 timeout**；主进程逐 delta IPC 无批处理（渲染层才 50ms 合并）；落库输出无截断。

### 4.5 飞书 / Cron 链路

- 飞书：token 提前 5min 刷新 + in-flight 去重 ✅；消息队列串行+16 上限背压 ✅；dedup 500 条 FIFO ✅。缺口：API 401 无 clearTokenCache 自动重试。
- Cron：**错过调度无补偿**（node-cron 纯内存，睡眠/停机期间触发点静默丢失）；`webContents.send` 无 isDestroyed 守卫（熔断分支在 try 块外，异常逃逸到 node-cron 回调）。

### 4.6 测试覆盖缺口

159 文件 / 约 2,575 用例，单测密度优秀（约 1 用例/20 行）。盲区：
- **`pi-ai/streaming.ts` 零覆盖**——所有 LLM 流式输出的底层通道（高风险）
- feishu-bot 子模块（message-queue/dedup-cache/event-handler）、mcp/pool、bootstrap/（恰是历史数据丢失 bug 所在层）
- 打包产物冒烟（CI 从不执行 electron-builder + 安装包启动）、GUI e2e、18 个提示词质量零测试
